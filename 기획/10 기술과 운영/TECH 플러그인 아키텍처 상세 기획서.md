## 1. 설계 목표

- 커스텀 HP, 전투, 장비, 상태이상, 증강, 시설, 발견과 Day 진행의 최종 권위자를 하나로 유지한다.
- 바닐라 이벤트와 외부 플러그인이 같은 공격·보상·아이템을 두 번 처리하지 못하게 한다.
- 서버 종료나 재접속으로 보상, 장비, 재료와 투표 결과가 중복되거나 소실되지 않게 한다.
- 고정 기지나 고정 임무 구역 없이 플레이어 주변과 시설망을 동적으로 추적한다.
- 모드와 리소스 팩 없이 GUI, 보스바, 액션바, 표시 엔티티와 바닐라 아이템으로 모든 핵심 기능을 제공한다.
- Day 50 이전 최종 진행과 미발견 콘텐츠의 직접 실행을 서버가 차단한다.
- Day 50 이후에도 최종 목표 완료 전까지 Day 상태와 위협 프로필을 저장·진행한다.
- 난이도 스키마 이동, Day 스킵 투표와 향후 Story 삽입 상태를 핵심 도메인과 분리해 복구 가능하게 한다.

## 2. 아키텍처 형태

초기 구현은 `모듈형 모놀리식 플러그인`을 사용한다. 하나의 `wsplugin` 안에서 기능 패키지와 서비스 경계를 분리하되, 전투처럼 틱 단위 일관성이 필요한 기능을 별도 플러그인 간 이벤트 통신에 의존시키지 않는다.

### 2.1 권장 패키지 구조

```text
com.lsc.corp.wsplugin
├─ bootstrap        플러그인 수명주기, 의존성 조립, 마이그레이션
├─ api              안정된 내부 API와 외부 연동 API
├─ session          회차, 파티, Day, 난이도, 스킵, 최종 목표, 일시중단
├─ classification   콘텐츠 분류, 난이도 스키마, 규칙 모드
├─ story            빈 Story 상태, 챕터·오브젝트·인물 이벤트 접점
├─ player           플레이어 프로필, 생명 상태, 레벨, 스탯
├─ combat           피해, AP, 회피, 방어, 패링, 타격 실행
├─ status           상태이상, 저항, 3초 CC 체인
├─ breaksystem      브레이크, 그로기, 패턴 중단
├─ equipment        장비 원장, 슬롯 동기화, 제작, 강화, 재련
├─ augment          개인·파티 증강, 후보, 투표, 등급 잠금
├─ discovery        발견 노드, 단서, 소급 판정, 해금
├─ resource         자원 노드, 채집, 드롭, 재생
├─ facility         시설 인스턴스, 네트워크, 피해, 대기열
├─ corruption       세계·시설망·플레이어·지역 오염
├─ encounter        동적 사건, 야간 압박, 보스 전장
├─ reward           기여도, 보상 원장, 필요·양보·귀속
├─ ui               인벤토리 GUI, 보스바, 액션바, 메시지
├─ persistence      SQLite, 스냅샷, 트랜잭션, 마이그레이션
├─ integration      MagicSpells 등 선택 연동 어댑터
├─ admin            검사·복구·운영 명령과 감사 로그
└─ common           ID, 시간, 난수, 수학, 공간 인덱스
```

### 2.2 의존 방향

```text
Paper 이벤트·외부 플러그인
        ↓
입력/연동 어댑터
        ↓
도메인 명령 서비스
        ↓
도메인 상태 + 규칙 엔진
        ↓
저장 트랜잭션 / UI 결과 / 도메인 이벤트
```

- 도메인 코드는 Bukkit 이벤트 객체를 장기 보관하지 않는다.
- UI는 도메인 상태를 변경하지 않고 명령을 요청한다.
- 저장 계층은 전투 공식을 알지 못하며 도메인 스냅샷과 원장만 저장한다.
- 외부 플러그인은 WildSurvival의 최종 피해·상태·보상 값을 직접 확정하지 않는다.

## 3. 핵심 모듈 책임

| 모듈 | 권위 데이터 | 외부에 제공할 명령·조회 |
|---|---|---|
| Session | 회차 상태, 멤버, Day, 단계, 스킵, 최종 목표 | 시작·중단·재개·투표·Day 전환·최종 완료 |
| Classification | 콘텐츠 분류, 난이도 ID·스키마, 규칙 모드 | 회차 계약 생성·마이그레이션·통계 라우팅 |
| Budget | 정책 리비전, 허용 범위, Day·도메인별 잠긴 예산·잔여 | 프로필 검증·잠금·예약·소비·감사 조회 |
| Story | 챕터·오브젝트·인물·플래그의 선택 상태 | 도메인 이벤트 소비·상태 조회·연출 요청 |
| Player | 생명 상태, 레벨, EXP, 스탯 투자 | 성장·부활·최종 스탯 조회 |
| Combat | HP, AP, 전투 상태, 공격 실행 | 피해·회복·보호막·행동 요청 |
| Equipment | 장비 인스턴스, 장착 원장, 귀속 | 장착·제작·강화·재련 |
| Augment | 등급 잠금, 후보, 선택, 투표 | 후보 생성·리롤·선택·교체 |
| Discovery | 노드 상태, 증거, 해금 | 증거 기록·소급 검사·힌트 공개 |

| Corruption | 오염 저장값과 지역 파생 | 증가·정화·단계 조회 |

같은 값을 두 모듈이 저장하지 않는다. 예를 들어 장비의 고정 HP는 Equipment가 원본을 저장하고 Player/STAT가 최종 수치 계산 시 조회한다.

## 4. 플러그인 수명주기

### 4.1 `onLoad`

1. 플러그인 데이터 경로와 설정 리비전을 확인한다.
2. 외부 연동 플러그인의 존재 여부만 탐지한다.
3. Paper 이벤트 등록이나 월드 접근은 수행하지 않는다.

### 4.2 `onEnable`

1. 설정 스키마, 콘텐츠 데이터와 `budgetPolicyRevision`을 검증한다.
2. SQLite 연결을 열고 마이그레이션 락을 획득한다.
3. 데이터베이스 마이그레이션과 미완료 트랜잭션 복구를 수행한다.
4. 활성 회차 스냅샷을 읽고 월드 UUID·데이터 리비전을 검증한다.
5. 도메인 서비스와 저장소를 조립한다.
6. Paper 리스너, 명령, GUI, 틱 스케줄러를 등록한다.
7. 온라인 플레이어를 회차 원장과 동기화한다.
8. 검증 완료 전까지 회차 진행은 `RECOVERING`으로 잠근다.

### 4.3 `onDisable`

1. 신규 전투·GUI·제작 명령 접수를 중단한다.
2. 현재 틱의 도메인 명령 큐를 제한 시간 안에 비운다.
3. 활성 회차와 플레이어의 긴급 스냅샷을 저장한다.
4. 저장 완료 여부와 마지막 트랜잭션 순번을 종료 표식에 기록한다.
5. 스케줄러, 보스바, 표시 엔티티와 외부 연동을 정리한다.
6. SQLite 체크포인트 후 연결을 닫는다.

비정상 종료는 마지막 확정 트랜잭션 이후 미확정 작업을 재실행하지 않고, 트랜잭션 상태에 따라 완료 또는 취소한다.

## 5. 스레드와 틱 규칙

### 5.1 메인 스레드 전용

- Bukkit/Paper 월드·엔티티·인벤토리 접근
- 공격 대상 레이 트레이스와 충돌 후보 확정
- 블록 설치·파괴, 시설 외형 변경
- GUI 열기·닫기·아이템 변경
- 엔티티 생성·삭제·텔레포트
- 최종 도메인 상태 적용과 이벤트 발행

### 5.2 비동기 허용

- SQLite 읽기·쓰기 준비와 배치 커밋
- 콘텐츠 파일 파싱과 정적 검증
- 순수 수치 시뮬레이션
- 오프라인 통계 집계와 관리자 보고서
- Paper 객체를 포함하지 않은 스냅샷 직렬화

비동기 작업은 엔티티 객체 대신 UUID, 월드 UUID, 좌표 값과 불변 스냅샷만 사용한다. 완료 결과는 메인 스레드에서 리비전을 다시 확인한 뒤 적용한다.

### 5.3 틱 작업 예산

| 작업 | 주기 | 기본 상한 |
|---|---:|---:|
| 입력·공격 명령 | 매 틱 | 플레이어당 공격 실행 1회 |
| 활성 투사체 | 매 틱 | 회차 전체 256개 |
| 지속 영역 | 매 틱 또는 2틱 | 회차 전체 64개 |
| 상태이상 갱신 | 매 틱 집계 | 플레이어 64개, 적 32개 |
| 시설·사건 공간 검사 | 5~20틱 | 한 틱 후보 검사 예산 분할 |
| 개인 오염 | 100틱 | 플레이어별 1회 |
| 자동 저장 | 20초 또는 중요 이벤트 | 한 번에 하나의 저장 배치 |

- 수치는 초기 안전 상한이며 `BALANCE/PERF` 측정으로 조정한다.
- TPS가 18 미만이면 파티클과 비핵심 후보 검색을 먼저 줄인다.
- TPS가 15 미만이면 신규 일반 적 생성량을 줄이고 위협 예산을 삭제하지 않은 채 다음 웨이브로 이월하거나 정예도에 재분배한다.
- 피해, 투표, 보상과 Day 시간은 TPS 저하로 중복 실행해서는 안 된다.

## 6. 시간 모델

| 시간 종류 | 기준 |
|---|---|
| 전투 틱 | 서버 틱 순번 |
| 쿨타임·Day·투표 | 단조 증가 시간 `nanoTime` 계열을 밀리초로 래핑 |
| 저장 시각 | UTC `Instant` |
| 결정 순서 | 회차별 증가 `commandSequence` |

- 낮은 TPS에서도 쿨타임과 Day는 실제 경과 시간 기준을 사용한다.
- Day 스킵은 남은 실제 시간을 생산·재생·쿨타임에 더하지 않고 `DAY_TRANSITION` 명령만 앞당긴다.
- 다단 공격의 같은 틱 순서는 `commandSequence`, 실행 ID, 타격 순번으로 확정한다.
- 서버 재시작 중 오프라인 시간을 Day 진행이나 상태 피해에 더하지 않는다.

## 7. ID와 데이터 리비전

| ID | 형식 | 목적 |
|---|---|---|
| `runId` | UUID/ULID | 회차 |
| `transactionId` | UUID | 원자 작업과 중복 방지 |
| `executionId` | runId+sequence | 공격·스킬 실행 |
| `hitId` | executionId+index | 개별 타격 |
| `itemInstanceId` | UUID | 장비·고유 아이템 |
| `facilityInstanceId` | UUID | 시설 |
| `facilityNetworkId` | UUID | 연결 시설망 |
| `encounterId` | runId+Day+sequence | 공세·사건·보스 |
| `rewardId` | sourceId+rewardRevision | 보상 지급 |

모든 콘텐츠 템플릿은 `id`, `schemaVersion`, `contentRevision`을 가진다. 활성 회차는 시작 시 콘텐츠 리비전을 고정하고, 핫 리로드가 기존 회차의 수치 의미를 바꾸지 않게 한다.

## 8. 저장 구조

### 8.1 저장 매체

| 데이터 | 저장 방식 |
|---|---|
| 콘텐츠 정의 | Git으로 관리하는 YAML 또는 JSON |
| 회차·플레이어·원장 | SQLite WAL |
| 긴급 복구 스냅샷 | 압축 JSON 또는 바이너리 스냅샷 |
| 운영 로그 | 회전 로그 + SQLite 감사 테이블 |
| 비밀 키 | 저장소 밖 서버 설정, Git 제외 |

SQLite를 단일 권위 저장소로 사용하고 YAML을 런타임 플레이어 데이터 저장소로 사용하지 않는다. 멀티 서버 운영으로 전환하면 DB 락·분산 리더 선출·메시지 전달 계층을 별도 설계해야 한다.

### 8.2 주요 테이블

```text
schema_version
runs
run_participants
day_skip_votes
day_transition_ledger
final_objective_states
player_states
player_stats
items
equipment_loadouts
skill_loadouts
quick_item_loadouts
player_input_preferences
augment_tier_locks
player_augments
party_augments
discoveries
discovery_evidence
facilities
facility_networks
facility_jobs
corruption_states
encounters
contribution_snapshots
reward_ledger
reward_grants
reward_remainders
loot_preferences
transactions
outbox_events
story_runs
story_chapter_states
story_object_states
story_character_states
admin_audit
```

큰 컬렉션은 JSON 한 칸에 전부 넣지 않고 조회·복구 단위에 맞춰 분리한다. 단, 스킬의 정적 효과 블록처럼 서버가 부분 갱신하지 않는 작은 구조는 리비전과 함께 JSON으로 저장할 수 있다.

`contribution_snapshots`는 원천·플레이어·기여 축별 확정 합계와 생명 상태를, `reward_grants`는 공용·개인·고유 하위 지급 키를 저장한다. `reward_remainders`는 소수 공용 재료 배율의 이월값을, `loot_preferences`는 고유 장비 태그별 자동 필요 설정을 저장한다. 상세 원시 기여 사건은 활성 원천 복구에 필요한 범위만 유지하고 정산 후 압축한다.

`runs`는 `content_category`, `difficulty_id`, `difficulty_schema_version`, `game_mode`, `current_day`, `day_era`를 별도 열로 가진다. 난이도 스키마 v1→v2 변환은 `DIFFICULTY-001`의 일대일 매핑을 한 트랜잭션으로 적용하며, 원본 ID를 감사 기록에 남긴다.

Story 콘텐츠가 아직 없으면 `story_runs.content_revision = EMPTY`와 빈 상태만 저장한다. Story 테이블 오류가 회차·전투·보상 원장을 덮어쓰거나 최종 목표를 승인할 수 없다.

### 8.3 트랜잭션 상태

```text
PREPARED → COMMITTED
         ↘ CANCELLED
```

- 제작, 강화, 재련, 장착, 보상, 증강 선택, 시설 설치·수리·철거는 트랜잭션 ID를 요구한다.
- `PREPARED`에서 자원·이전 상태와 기대 리비전을 기록한다.
- 도메인 검증과 DB 갱신이 성공하면 `COMMITTED`로 확정한다.
- 서버 재시작 시 `PREPARED` 작업은 실제 월드/PDC 상태와 기대 리비전을 비교해 한 번만 완료하거나 취소한다.
- 같은 `rewardId` 또는 `transactionId`의 두 번째 요청은 기존 결과를 반환한다.

## 9. 결정론적 난수

```text
seed = hash(runSeed, domainId, milestoneOrDay, drawRevision)
```

- 증강 등급 잠금, 후보, 파티 동률, 보스 보상 후보와 동적 사건 선택은 도메인별 난수 스트림을 분리한다.
- 한 도메인의 재추첨 횟수가 다른 도메인의 결과를 바꾸지 않는다.
- 후보와 최종 결과뿐 아니라 사용한 seed key와 draw revision을 저장한다.
- 재접속·서버 재시작으로 이미 표시된 후보가 바뀌지 않는다.

## 10. 콘텐츠 데이터 로딩

### 10.1 로드 단계

1. 파일 문법 검사
2. 스키마 버전 검사
3. ID 중복·참조 누락 검사

Day 1~20 최초 구현 입력은 `DATA-REVISION-001`의 `ws-content-r1`을 사용한다. 파일 해시, 도메인 번들, 참조·합계 검증과 새 회차 전용 활성 정책은 해당 문서와 manifest를 따른다.

## 12. 장비 슬롯과 입력 계약

### 12.1 슬롯

- `MAIN_WEAPON`은 바닐라 핫바 슬롯 `0`에 동기화한다.
- `OFF_WEAPON`은 오프핸드 식별값 `-106`에 동기화한다.
- Bukkit 접근은 API의 플레이어 인벤토리·EquipmentSlot을 사용하고, `-106`은 저장·명령·프로토콜 의미 ID로만 취급한다.
- 서버 장착 원장이 권위이며 실제 인벤토리가 다르면 다음 틱에 복원한다.
- 핫바 `1~8`은 완전한 바닐라 자유 슬롯이며 프록시 아이템을 삽입하지 않는다.
- 현재 선택 슬롯이 `0`일 때만 전투 라우터가 L/R/Shift 조합/F를 소비한다. `1~8`에서는 채굴·설치·섭취 등 바닐라 행동으로 보낸다.
- 슬롯 `0/-106`의 숫자 키, F키, 드래그, 쉬프트 클릭, 디스펜서와 사망 드롭 장비 우회만 차단한다.

### 12.2 공격 우선순위

```text
열린 WildSurvival GUI
→ 퀵 아이템 사용·취소
→ 구조·시설 상호작용
→ 보조무기·방어·패링
→ 회피·W1~W3·C1~C4 액티브 스킬
→ 공격 가능 개체 레이 트레이스
→ 장착 무기 BASIC_ATTACK/권투 가상 공격
→ 허용된 바닐라 블록 파괴
```

- 곡괭이는 공격 가능 개체 레이 트레이스가 성공하면 전투를 우선하고, 실패한 경우에만 블록 채굴로 내려간다.
- 삼지창의 바닐라 투척·급류·충성 실행은 차단하고 커스텀 실행과 회수 상태로 변환한다.
- 주무기 원장과 실제 슬롯 0이 모두 비어 있으면 권투 가상 프로필을 활성화한다.
- 단검은 검 Material, 둔기는 철퇴 Material을 사용하며 PDC 무기군 태그로 바닐라 종류와 구분한다.

### 12.3 스킬·퀵 아이템 입력 라우터

- 장착 무기의 좌클릭은 `WeaponBasicCommand`로 변환하며 바닐라 근접·발사·투척 피해 이벤트를 취소한다.
- 권투 좌클릭은 `UnarmedBasicCommand`로 분리하며 장비 인스턴스 ID를 요구하지 않는다.
- 프로토타입 무기 입력은 `L=BASIC`, `R=W1`, `Shift+L=W2`, `Shift+R=W3`, `F=W3 문맥 입력`으로 라우팅하고 `Shift+F`는 메뉴가 우선한다.
- `PlayerItemHeldEvent`는 이전 슬롯과 새 슬롯만 제공하므로 숫자키·휠 원인을 판별했다고 가정하지 않는다. 기본 `SNEAK_SELECT` 또는 `SELECT_CONFIRM`만 안전 모드로 취급한다.
- 이전 슬롯 `0`+웅크림+새 슬롯 `1~4`는 C1~C4, 새 슬롯 `5~8`은 Q1~Q4로 해석하고 다음 틱 슬롯 `0`으로 복원한다.
- Q1~Q4는 장비 GUI의 바인딩 ID와 개인 원장을 함께 검증하며 실제 핫바 아이템을 참조하지 않는다.
- 공용 액티브와 퀵 아이템이 같은 스택을 참조하면 원장 예약에 성공한 실행 하나만 커밋한다.

## 13. 공격 실행 파이프라인

```text
입력 수신
→ 사용 가능 상태 검사
→ 실행 ID 발급
→ 비용·쿨타임 PREPARE
→ 스탯 스냅샷
→ 공간 후보 수집
→ 관계·LOS·생명 상태·최대 대상 재검증
→ 회피·패링·방어
→ 피해·상태·브레이크 계산
→ HP/AP/상태 원자 적용
→ 기여·발동·전투 로그
→ 실행 COMMIT
```

- 한 `hitId`는 대상 하나에 한 번만 적용한다.
- MagicSpells가 생성한 충돌은 후보일 뿐이며 마지막 다섯 단계를 건너뛸 수 없다.
- 기본 아군 공격은 관계 필터에서 제외한다.
- 전술 모드는 30% 피해·30% 강한 CC·50% 이동·브레이크와 HP 1 비치명 규칙을 최종 계산에서 한 번 적용한다.

## 14. GUI 프레임워크

### 14.1 공통 규칙

- 서버가 발급한 `guiSessionId`, 플레이어 UUID, 화면 종류와 데이터 리비전을 저장한다.
- 표시 아이템에는 클릭 명령 ID만 넣고 실제 값은 서버 세션에서 조회한다.
- 클릭 때 현재 도메인 리비전을 다시 검사한다.
- GUI 종료는 미확정 임시 변경을 폐기한다.
- 확인이 필요한 희귀 자원 소비와 귀속은 확인 화면을 한 단계 추가한다.

### 14.2 리소스 팩 없는 표시

| 의미 | 표현 |
|---|---|
| 선택 가능 | 일반 아이템 + 초록 이름 + `선택 가능` 로어 |
| 잠김 | 회색 유리판 + 잠금 사유 |
| 위험 | 붉은 이름 + 경고 로어 + 소리 |
| 등급 | 바닐라 아이템 색·이름 접두어·로어 텍스트 |
| 페이지 | 화살·책·종이 아이템 |
| 확정 | 라임 콘크리트/에메랄드 계열 |
| 취소 | 배리어/붉은 콘크리트 계열 |

색상만으로 상태를 구분하지 않고 텍스트, 기호와 소리를 함께 사용한다.

## 15. PDC와 아이템 무결성

필수 PDC 키:

```text
ws:item_instance_id
ws:template_id
ws:content_revision
ws:rarity
ws:weapon_type
ws:owner_run_id
ws:bound_player
ws:item_revision
ws:signature
```

- 서명은 서버 외부 비밀 키로 핵심 필드를 HMAC 처리한 값이다.
- 인벤토리 이동, 장착, 제작, 드롭, 보관과 재접속 때 서명을 검증한다.
- 같은 instance ID가 두 위치에서 발견되면 두 아이템을 모두 사용 잠금하고 원장과 일치하는 하나만 복구한다.
- 아이템 스택 병합으로 instance ID가 합쳐지지 않게 콘텐츠 장비는 수량 1을 강제한다.
- PDC가 사라진 아이템은 바닐라 아이템으로 강등하지 않고 격리 GUI로 이동한다.

## 16. 발견 시스템 구현 계약

- 발견 증거는 `evidenceType + subjectId + contextId + revision`으로 기록한다.
- 노드가 숨겨져 있어도 증거를 먼저 저장해 소급 판정한다.
- 핵심 노드는 최소 두 개의 조건 묶음 중 하나로 완료할 수 있게 `ANY_OF` 경로를 지원한다.
- 파티 공유 노드는 한 명의 유효 증거가 회차 전체에 적용된다.
- 개인 숙련 노드는 플레이어별로 유지한다.
- 힌트 단계는 실패 횟수, 경과 Day와 보유 증거 수로만 열며 정답 아이템 ID를 즉시 공개하지 않는다.

### 16.1 Story 삽입 계약

- Story 모듈은 `RUN_CREATED`, `DAY_STARTED`, `DISCOVERY_COMPLETED`, `FACILITY_BUILT`, `BOSS_SIGNAL_ACQUIRED`, `PLAYER_DOWNED`, `POST_50_ENTERED`, `FINAL_OBJECTIVE_READY`, `RUN_COMPLETED` 이벤트를 선택적으로 소비한다.
- 현재는 실제 서사·대사·챕터·오브젝트·인물 정의를 로드하지 않고 빈 상태와 no-op 소비자만 설계한다.
- Story 소비자는 원본 이벤트 결과를 취소하거나 장비·발견·보스·최종 목표 상태를 직접 변경할 수 없다.
- 향후 Story 리비전을 추가해도 활성 회차는 시작 시 고정한 Story 콘텐츠 리비전을 사용한다.

### 16.2 Day 스킵·최종 목표 계약

- 스킵 투표 결과는 `runId + targetDay + voteSequence`로 중복 방지한다.
- `SKIP_PREPARED`, `EXPEDITE_PENDING`, `DAY_TRANSITION`, `COMMITTED` 단계를 원장에 저장한다.
- `difficultyId == UNKNOWN` 또는 `gameMode == CHAOS`이면 도메인 명령 단계에서 거부한다.
- Day 50은 `FINAL_UNLOCK` 시대 전환일이며 `COMPLETED` 전이가 아니다.
- `currentDay`는 50을 초과할 수 있고, 최종 목표 완료 트랜잭션만 회차를 `COMPLETED`로 전환한다.

## 17. 동적 공간과 시설망

- 고정 임무 구역 대신 수명이 있는 `DynamicContext`를 사용한다.
- 문맥은 중심 원인, 후보 반경, 월드 UUID, 시작·종료 시각과 참여자 집합을 가진다.
- 시설망은 설치 좌표의 거리 그래프와 중계기 연결을 기준으로 계산한다.
- 압박 대상은 최근 사용, 시설 가치, 파티 거리, 위협도와 유효 경로를 점수화해 선택한다.
- 동적 보스 전장은 신호 사용 시 안전 공간 검사 후 생성하고 종료 시 임시 표시·보호 데이터만 제거한다.
- 청크를 영구 강제 로드하지 않고, 활성 플레이어·사건·시설 작업이 있을 때만 청크 티켓을 제한적으로 사용한다.

## 18. 외부 플러그인 연동

### MagicSpells

| 담당 가능 | 담당 금지 |
|---|---|
| 파티클·사운드 | 최종 피해 |
| 단순 투사체 이동 | 커스텀 HP 변경 |
| 1차 충돌 후보 | 상태이상 최종 적용 |
| 빔·지속 연출 | 브레이크·기여도·보상 |

- `softdepend`로 두고 없으면 WildSurvival Native 실행 또는 해당 연출의 단순 대체를 사용한다.
- 연동 버전이 맞지 않으면 관련 스킬 데이터 로드를 거부하고 명확한 오류를 출력한다.
- 연동 콜백은 실행 토큰을 요구하며 토큰 없는 외부 피해 요청은 거부한다.

새 외부 플러그인은 권한 경계, 장애 시 대체, 버전 호환과 중복 처리 테스트를 문서화한 뒤 추가한다.

## 19. 관리자 명령

정확한 명령 경로, 권한 노드, dry-run 확인 토큰과 증상별 복구 결정은 `OPS-001`을 단일 하위 기준으로 사용한다.

| 명령 범주 | 기능 |
|---|---|
| `inspect run` | 회차, Day, 멤버, 잠금 리비전 조회 |
| `inspect player` | 생명·장비·증강·발견·트랜잭션 조회 |
| `inspect item` | PDC, 서명, 소유권, 원장 위치 조회 |
| `inspect facility` | 시설·네트워크·작업·오염 조회 |
| `inspect day` | Day 시대·스킵 투표·전환 원장·최종 목표 조건 조회 |
| `inspect classification` | 콘텐츠 분류·난이도 스키마·원본 마이그레이션 조회 |
| `inspect story` | Story 리비전과 빈/활성 상태 조회, 내용 생성 기능 없음 |
| `recover transaction` | 미완료 트랜잭션 검사·안전 복구 |
| `recover item` | 중복·격리 아이템 판정 후 복구 |
| `validate content` | 콘텐츠 스키마와 참조 전체 검사 |
| `snapshot create` | 운영자 수동 복구 스냅샷 생성 |

- 모든 변경 명령은 실행자, 사유, 이전·이후 값과 트랜잭션 ID를 감사 로그에 남긴다.
- 일반 운영자는 직접 레벨·아이템을 조작하기보다 도메인 복구 명령을 사용한다.

## 20. 장애 복구 우선순위

1. 데이터베이스 스키마와 마지막 종료 표식 검사
2. 미완료 트랜잭션 복구
3. 회차·멤버·Day 스냅샷 복원
4. 장비 원장과 실제 인벤토리 대조
5. 시설 원장과 월드 블록 대조
6. 활성 사건·보스 복원 가능성 판정
7. 복원이 불안정한 사건은 보상 없이 안전 취소 또는 체크포인트 재개
8. 전체 검증 후 `RECOVERING` 해제

전멸, 보스 처치와 고유 보상 확정은 일반 체크포인트 롤백으로 되돌리지 않는다.

## 24. 완료 기준
